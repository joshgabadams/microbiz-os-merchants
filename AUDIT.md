## Stack identification

- **teller/** — standalone SPA: **React 19 + Vite 8 + react-router-dom 7**, client-side routing (`BrowserRouter`), served independently of any backend (own `vite dev`/static build) — not Blade, not Livewire, not Inertia. No SSR.
- **microbiz-os/** — **Laravel** (SQLite default) implementing FinCore-domain code directly (Teller/Vault/GL/Approvals/Balancing/Customer accounts/Fineract-client) inside `app/`. Auth is now **Sanctum** (bearer tokens). No separate "MicroBiz OS" abstraction layer, capability registry, or interface package was found — the checklist's OS/FINCORE distinction is not currently reflected in the code (see Security flags).
- No API wiring exists between the two repos yet — `teller/` has zero HTTP client code, even though the backend now has real, working endpoints it could call.

## Security flags

1. **Client-trusted identity on every "who did this" field except teller open/close.** `maker_id`, `checker_id` (`ApprovalController`), `performed_by` (`ApprovalController`, `CustomerCashController`), `balanced_by` (`BalancingController`), and `closed_by` (`BranchEodController`) are all read directly from the request body and only checked with `exists:users,id` — they are never cross-checked against `$request->user()->id`, the actual authenticated identity. Concretely: any authenticated (but otherwise unprivileged) API caller can submit a different, real user's ID as the `checker_id` on an approval, and the system will record that person as having approved it, even though they never made the call. `TellerController::open()`/`close()` do this correctly (`$request->user()->id`) — that pattern needs to be applied everywhere else that accepts an actor ID from the client.
2. **No server-side permission/role enforcement.** RBAC is entirely absent (no roles column, no Gate/Policy). Once #1 above is fixed, authentication would correctly identify *who* is calling — but nothing yet stops *any* authenticated user from approving floats, closing EOD, etc.
3. **Unauthenticated debug routes that mutate data** — `routes/web.php:9-64` (`/test-branch`, `/test-fineract`, `/test-gls`, `/test-ledger`), reachable via plain GET, no auth.
4. **GL journals table is broken on any already-migrated database** (see Table 2, GL posting row / `CHANGELOG.md` #1) — a financial-integrity defect, not just a UI gap; every vault deposit/withdrawal currently throws when it tries to post to GL on this DB.
5. **Fake client-side OTP** presented as a security control — `teller/src/components/TransferModal.jsx:32`.
6. **No committed secrets** in either repo — env-based config throughout, `.env` confirmed gitignored and untracked.

## Ranked gap list (top 10, ordered by how hard they block the current teller sprint)

1. Actor identity (`maker_id`/`checker_id`/`performed_by`/`balanced_by`/`closed_by`) must be derived from the authenticated Sanctum user, not accepted from the request body — closes the impersonation gap across `ApprovalController`, `CustomerCashController`, `BalancingController`, `BranchEodController`. Blocks trusting maker-checker at all, even though the workflow itself now exists.
2. Server-side permission/role enforcement (RBAC) — still completely absent; without it, "approve" being a distinct action from "make" doesn't actually restrict who can do it.
3. `gl_journals` table is broken on any already-migrated database — needs a new additive migration (per `CHANGELOG.md` #1); blocks trustworthy GL posting, which every vault transaction now depends on.
4. Frontend has no API layer at all — none of the real, working backend endpoints (teller open/close, approvals, float allocate/return, balancing) are wired to any screen yet.
5. Denomination-level cash counting doesn't exist anywhere, backend or frontend — `physical_cash` is always a single submitted number; blocks building a real reconciliation/close screen.
6. Frontend teller open/close and vault reconciliation screens are still unwired stubs/placeholders — needs building regardless of backend readiness.
7. Legacy dead code (`Reconciliation`/`ReconciliationService`, `TillTransactionService`/`till_transactions`, unfilled `CashAllocation`/`CashReturn` models — see `CHANGELOG.md` #2, #6, #7) should be removed so it doesn't get mistaken for the live path during rewiring.
8. Unauthenticated debug routes in `routes/web.php` that mutate data — remove or gate before any shared environment.
9. No live/real-time branch cash position aggregation endpoint (only EOD close exists) — needed to back the Branch dashboard screen with real data.
10. Receipts/print — no transaction receipt component on either side; only a vault-position report exporter exists on the frontend.
